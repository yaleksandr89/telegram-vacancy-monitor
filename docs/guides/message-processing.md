# Как приложение получает и обрабатывает вакансии

Когда вы отправляете или пересылаете вакансию боту, Телеграмм передаёт приложению обновление. Приложение сохраняет текст и создаёт задание на оценку. Результат отправляется в тот же чат после анализа.

## Что сохраняется

Для каждой вакансии SQLite хранит текст, идентификаторы сообщения и, если доступны, сведения об исходной пересланной публикации. Отдельно хранятся состояние оценки и её отправки.

В [схеме БД](../../src/Storage/SqliteSchema.php) этим соответствуют таблицы `messages` и `analysis_jobs`.

## Зачем нужен курсор

При локальном запуске приложение получает обновления методом `getUpdates`. У каждого обновления есть числовой `update_id`. **Курсор** — это сохранённое число, с которого нужно запросить обновления в следующий раз.

Пример:

1. Приложение получает обновление `104` с новой вакансией.
2. Записывает вакансию в SQLite, создаёт задание и сохраняет следующий курсор `105`.
3. Следующий запрос к Телеграмму начинается с `offset = 105`: повторно получать `104` больше не нужно.

Сохранение вакансии и продвижение курсора происходят вместе. Если запись не удалась, курсор остаётся прежним: Телеграмм сможет снова передать обновление. Если обновление уже сохранено, приложение не создаст вторую копию.

### Что означают `name` и `next_offset`

В таблице `cursor` хранится одна запись для локального получения сообщений:

| Столбец | Пример | Значение |
| --- | --- | --- |
| `name` | `main` | Название курсора. `main` — постоянное имя, а не имя бота или чата. |
| `next_offset` | `105` | Номер, который приложение передаст Telegram в следующем запросе `getUpdates`. |

**`next_offset` вычисляется из `update_id`, а не из номера сообщения.** Если получено обновление `update_id = 104`, приложение сохраняет `next_offset = 105`. Даже при повторном получении старого `update_id` значение курсора не уменьшается.

Разные идентификаторы выполняют разные задачи:

| Поле | Что обозначает |
| --- | --- |
| `update_id` в обновлении Telegram | Номер события, из которого вычисляется `next_offset`. |
| `recipient_message_id` в таблице `messages` | Номер сообщения в чате с ботом. Не используется для расчёта курсора. |
| `origin_message_id` в таблице `messages` | Номер исходной публикации в канале, если Telegram передал его при пересылке. Не используется для расчёта курсора. |

Например, обновление `104` может содержать сообщение `312` в чате с ботом и исходную публикацию `87` в канале. Курсор станет `105`. Номера `312` и `87` на него не влияют.

Курсор не является номером вакансии или источника. Он нужен только для последовательного приёма обновлений через `getUpdates`. См. [`SqliteInboxRepository::nextOffset()` и `applyUpdate()`](../../src/Storage/SqliteInboxRepository.php).

## А если используется вебхук?

При вебхуке Телеграмм отправляет запросы на сервер. Они могут прийти повторно или в другом порядке. Вместо курсора приложение записывает каждый `update_id` в таблицу `received_updates` и проверяет, не принималось ли это обновление раньше.

Например, запрос с `update_id = 205` успешно записан и Телеграмм получает ответ HTTP 204. Если такой же запрос придёт снова, новое задание не создаётся. Если запись в БД не удалась, сервер возвращает ошибку, и Телеграмм может повторить доставку.

Механизм реализован в [`SqliteInboxRepository::applyWebhookUpdate()`](../../src/Storage/SqliteInboxRepository.php) и [`WebhookReceiver`](../../src/Application/WebhookReceiver.php).

## Какие вакансии считаются повторными

Приложение использует два вида идентификаторов:

- **Сообщение в чате с ботом.** Повторная доставка того же сообщения с тем же ID не создаёт другую вакансию.
- **Исходная пересланная публикация.** Если Телеграмм передал идентификаторы исходного канала и публикации, повторная пересылка этой же публикации не создаёт новую оценку, даже если у нового сообщения в чате с ботом другой ID.

Например, вы переслали вакансию из канала сегодня, а завтра отправили её ещё раз. Если сохранились идентификаторы исходной публикации, приложение ответит «Эта публикация уже сохранена.». **Одинаковый текст сам по себе не считается повтором:** два разных объявления могут содержать один и тот же текст.

Правила находятся в [`IncomingUpdateProcessor`](../../src/Application/IncomingUpdateProcessor.php), а уникальные ключи сообщений — в [`SqliteSchema`](../../src/Storage/SqliteSchema.php).

## Что происходит после сохранения

1. Бот подтверждает: «Вакансия сохранена.».
2. Приложение анализирует сохранённый текст с учётом профиля и инструкций. На сервере это делает обработчик, запускаемый через cron.
3. Готовая оценка записывается в SQLite и отправляется в Телеграмм.
4. Если отправка временно не удалась, приложение повторяет **отправку сохранённого результата**, не запрашивая новую оценку.
5. Если процесс прервался, незавершённая обработка продолжится после следующего запуска с учётом оставшихся попыток.

Уведомление о начале анализа может не прийти при сбое связи, хотя сама оценка продолжится. Если попытки окончательно закончились, повторный анализ автоматически не запускается. В редком случае, когда Телеграмм получил сообщение, но подтверждение не дошло до приложения, итоговое уведомление может повториться.

Состояние анализа и доставки хранит [`SqliteAnalysisRepository`](../../src/Storage/SqliteAnalysisRepository.php); действия выполняет [`VacancyAnalysisPipeline`](../../src/Application/VacancyAnalysisPipeline.php). [Структура оценки и уведомлений](../reference/analysis-result.md).
