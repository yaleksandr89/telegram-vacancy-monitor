# Webhook и cron на VDS

Приложение использует один PHP core и одну БД `var/vacancies.sqlite`:
PHP-FPM принимает сообщения, CLI cron выполняет существующий AI pipeline.
Источники и разрешённый отправитель остаются прежними. Передача данных
облачному AI не включается этим переключением; сохраняйте согласованные
настройки провайдера и профиля.

## Среда и приватные файлы

Нужны PHP 8.5 CLI и FPM с `curl`, `json`, `mbstring`, `PDO`, `pdo_sqlite`,
Composer и HTTPS с действительным сертификатом. Зависимости устанавливаются
из `composer.lock` через `composer install --no-dev --prefer-dist --optimize-autoloader`.
Проверяйте расширения и для CLI, и для FPM. Composer не является частью обработки
HTTP-запросов или cron. Отдельный HTTP-сервер приложение не запускает.

DocumentRoot должен указывать **строго на `public/`**. Единственный PHP endpoint —
`/webhook.php`; запретите листинг каталогов и выполнение иных PHP-путей.
Не настраивайте alias или fallback в корень проекта. `config/`, `vendor/`,
`var/`, `.git/` и исходники не должны быть доступны по HTTP. Ограничьте тело
запроса на HTTP-сервере до 256 KiB; приложение дополнительно читает не более
256 KiB + 1 байта и отклоняет превышение. FPM: `display_errors=Off`;
не записывайте тела запросов, secret header, токены или тексты вакансий в логи.

Вне DocumentRoot владелец создаёт приватные `config/bot.ini`,
`config/profile/local/candidate.md` и `config/profile/local/instructions.md`.
Они исключены из Git. В INI сохраняются разрешённый пользователь и действующие
параметры AI; добавляются:

```ini
TELEGRAM_RECEIVE_MODE = "webhook"
TELEGRAM_WEBHOOK_SECRET = ""
```

Пустое значение выше — образец: задайте отдельный случайный секрет длиной
1–256 символов из `A–Z`, `a–z`, `0–9`, `_`, `-`. Передавайте его в `secret_token`,
а не в URL webhook. В webhook-режиме `run` и `identify` завершаются с подсказкой;
`work-once` не вызывает `getUpdates`. Без новой настройки старый INI означает polling.

## Права и SQLite

CLI и FPM должны работать с **одним абсолютным путём проекта и одной БД**.
Предпочтителен отдельный непривилегированный пользователь приложения для cron
и выделенного FPM pool. Ему нужны чтение кода/`vendor/`/INI, чтение профиля для CLI,
запись в БД и её каталог `var/` для SQLite journal и файла `bot.lock`.
Остальным пользователям доступ к конфигурации и данным не выдаётся.

Если владельцы CLI/FPM различаются, оператор заранее задаёт точечные ACL для
нужных файлов и каталога, включая права на вновь создаваемые SQLite journal.
CLI/FPM создают приватные файлы с `umask(0077)`; одной общей группы без настройки
наследования ACL недостаточно. Не применяйте рекурсивные `chown`/`chmod` к проекту.
Проверьте запись SQLite от обеих учётных записей. Сбой доступа/занятая SQLite
даёт HTTP 503, а не успешное подтверждение; ожидание блокировки SQLite — до 5 секунд.
Сетевые вызовы выполняются вне транзакций БД.

До регистрации webhook выполните один `php bin/bot.php work-once` от пользователя
cron: он проверяет профиль/настройки и добавочно инициализирует схему. Он также
обработает уже ожидающие задания. Существующие сообщения и terminal failed jobs
не пересоздаются; перед изменением схемы используйте обычную резервную копию БД.
Webhook сам не создаёт отсутствующую БД.

## Переключение и cron

1. Остановите локальный polling. Подготовьте FPM, HTTPS, доступы и webhook-INI.
2. Проверьте, что POST без секрета получает 403, другой метод — 405,
   а приватные каталоги недоступны по HTTP. Не используйте реальные тексты в пробах.
3. Владелец регистрирует webhook методом
   [setWebhook](https://core.telegram.org/bots/api#setwebhook): `url` — HTTPS-адрес
   `/webhook.php`, `secret_token` — значение из INI, `allowed_updates=["message"]`,
   `drop_pending_updates=false`. Для небольшого личного бота можно задать
   `max_connections=1`. Не помещайте токен в shell history, URL сайта, отчёты или логи;
   регистрацию выполняйте своим защищённым способом обращения к Bot API.
4. Через [getWebhookInfo](https://core.telegram.org/bots/api#getwebhookinfo)
   проверьте URL, `pending_update_count` и ошибки доставки. Не публикуйте сырой ответ.
5. Cron запускает команду раз в минуту от назначенного пользователя, с абсолютными
   путями PHP 8.5 и проекта. Шаблон строки (пути заменяет владелец):

   ```cron
   * * * * * /absolute/path/to/php8.5 /absolute/path/to/project/bin/bot.php work-once
   ```

`work-once` делает `recover()` под общей блокировкой `var/bot.lock`, затем не более
10 вызовов `processPending`. Через 20 секунд новые вызовы не начинаются;
начатый AI-запрос завершается в рамках `AI_REQUEST_TIMEOUT_SECONDS` (30–1800).
Если блокировка занята, tick пропускается без восстановления активного задания.
После аварии следующий tick учитывает прерванную попытку и действующую задержку retry.
Проверяйте закрытый вывод cron; он не должен публиковаться HTTP-сервером.

Webhook сохраняет update, сообщение и job одной транзакцией; 204 возвращается
после коммита. Повторный update не создаёт job, update_id не обязаны идти по порядку.
При не-2xx Телеграмм повторяет доставку ограниченное время, поэтому проверяйте
ошибки своевременно. Повтор уже сохранённого update не повторяет подтверждение.

Обычный порядок: «Вакансия сохранена.» → уведомление старта → итог.
Webhook не запускает AI: ожидание зависит от cron и очереди. Подтверждение сохранения
отправляется best-effort после коммита; при сбое отправки данные остаются в БД.
Уведомление старта имеет одну **попытку** на вакансию, даже при retry/restart.
Сбой между persisted claim и отправкой может оставить его недоставленным;
это не гарантия доставки ровно один раз. Отказ предфильтра не вызывает этот текст.

## Возврат к polling

Остановите cron и дождитесь завершения активного воркера. Владелец вызывает
[deleteWebhook](https://core.telegram.org/bots/api#deletewebhook) с
`drop_pending_updates=false`, затем проверяет пустой URL через `getWebhookInfo`.
После завершения входящих FPM-запросов переключите INI на
`TELEGRAM_RECEIVE_MODE="polling"`, выключите публичный endpoint и только затем
запускайте `php bin/bot.php run`. Не запускайте две копии с одним токеном.
Сохраните ту же БД и `var/bot.lock`: задания продолжат обработку; повторы уже
сохранённых сообщений отсекутся уникальными ключами. Не очищайте `cursor`,
`received_updates` или сообщения вручную. Приложение не вызывает set/deleteWebhook.

## Ручной smoke владельца

- Проверить HTTPS, недоступность приватных путей, HTTP 403 без секрета и 405 для GET.
- Отправить искусственную вакансию разрешённым пользователем: подтверждение приходит
  после сохранения; AI начинается через cron, затем приходит итог.
- Проверить повтор пересылки и отказ чужому отправителю без нового AI-job.
- Во время активного AI запустить второй `work-once`: он пропускает tick;
  после завершения очередной cron продолжает очередь без повторной оценки готового результата.
- Проверить `getWebhookInfo` и отсутствие ошибок SQLite/прав; при необходимости
  выполнить описанный возврат к polling с сохранением ожидающих обновлений.
